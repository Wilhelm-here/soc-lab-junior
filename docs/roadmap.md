# Домашний SOC-стенд → портфолио junior: roadmap

**Для кого:** junior / SOC L1, который хочет на собеседовании показать не «я поставил Wazuh», а «я умею расследовать и настраивать детекты».
**Бюджет времени:** 28–34 часа = 3 недели по ~10 часов. Есть урезанная версия на 8 часов (см. §12).
**Бюджет денег:** 0 ₽, если есть ПК с 16+ ГБ RAM. 250–350 $ — если покупать б/у мини-ПК.

---

## 1. Результат, к которому идём (Definition of Done)

К концу проекта у тебя есть **один git-репозиторий**, в котором:

- [ ] `README.md` — схема стенда, что зачем, ограничения, «что бы сделал иначе»;
- [ ] `docs/architecture.md` — сети, VM, ресурсы;
- [ ] `docs/telemetry-matrix.md` — таблица «источник → Event ID → что вижу → проверено»;
- [ ] `reports/` — **3 инцидента** по 1–2 страницы;
- [ ] `detections/` — **5 детектов** (Sigma + карточка + результат проверки);
- [ ] `evidence/` — скриншоты и выгрузки алертов (без секретов и персональных данных);
- [ ] **видео 5 минут** — атака → алерт → разбор;
- [ ] **one-pager PDF** — 1 страница для собеседования.

Критерий «готово» для всего проекта: **незнакомый человек открывает README и за 3 минуты понимает, что ты делал и зачем.** Если нет — проект не готов, сколько бы VM ни работало.

## 2. Выбор трёх техник (сделай это до сборки стенда)

Три атаки должны бить по **разной логике детекта** — тогда в портфолио видно диапазон.

| # | Техника | Что тренирует | Почему она |
|---|---|---|---|
| 1 | `T1059.001` PowerShell | сигнатурный детект по командной строке | базовая грамотность, все её знают, легко проверить |
| 2 | `T1053.005` Scheduled Task | детект по событию создания объекта | persistence, Security 4698 + Sysmon 1 |
| 3 | `T1110.003` Password Spray | **пороговый** детект | сразу появляется разговор про FP и alert fatigue — это то, что отличает L1 от «нажимателя кнопок» |

Бонус, если останется время: `T1003.001` LSASS — почти всегда превращается в историю «детекта не было, потому что в Sysmon-конфиге не был включён ProcessAccess». Такая история на собеседовании стоит дороже трёх успешных.

## 3. Фазы

### Фаза 0. Подготовка — 1–2 ч

1. Создай репозиторий `soc-lab-junior` (GitHub/GitLab), приватность не нужна — это портфолио.
2. Сразу создай структуру папок из §5 и пустой README с планом.
3. Заведи `docs/journal.md` — короткие записи «что делал / что сломалось / как починил» по датам. Это сырьё для README и для историй на собесе.
4. Проверь железо: `RAM ≥ 16 ГБ` (лучше 32), свободно ≥ 150 ГБ на SSD.

**DoD:** репозиторий существует, в нём README и journal, техники выбраны.

---

### Фаза 1. Стенд — 5–7 ч

**Вариант А (рекомендуемый): отдельный ПК + Proxmox VE**
1. Proxmox с флешки (Ventoy + ISO). Статический IP, доступ к веб-интерфейсу `https://<ip>:8006`.
2. Создай внутренний бридж `vmbr1` **без физического порта** — это изолированная лабораторная сеть `10.10.10.0/24`.
3. VM:
   - **Ubuntu Server 24.04** — 4 vCPU / 8 ГБ / 100 ГБ (SIEM);
   - **Windows 11 Enterprise Evaluation** — 2 vCPU / 4–6 ГБ / 60 ГБ (жертва);
   - **Kali Linux** — 2 vCPU / 4 ГБ / 40 ГБ (атакующий).
4. Снапшот каждой VM после установки, имя `base-clean`.

**Вариант Б (нет отдельного ПК): VMware Workstation / Hyper-V на рабочей машине.** Те же три VM, сеть — Host-only (`VMnet1`), интернет включаешь только на время обновлений. Минус: медленнее и снапшоты неудобнее, но для портфолио достаточно.

**Изоляция — обязательна.** Проверка: с Windows-жертвы `ping <IP домашнего роутера>` **не** проходит, а `ping 10.10.10.10` (SIEM) проходит. Если это не так — не двигайся дальше, иначе первый же тест «малвари» пойдёт в домашнюю сеть.

**Wazuh (all-in-one) на Ubuntu:**
```bash
# на индексере до установки
sudo sysctl -w vm.max_map_count=262144
echo 'vm.max_map_count=262144' | sudo tee -a /etc/sysctl.conf

# актуальную ветку версии смотри на documentation.wazuh.com
curl -sO https://packages.wazuh.com/4.14/wazuh-install.sh
sudo bash wazuh-install.sh -a
```
Пароли установщик печатает в конце — сохрани их в менеджер паролей, **не в репозиторий**. Дальше: `https://10.10.10.10`.

**DoD:** три VM живы, изоляция проверена, дашборд Wazuh открывается, снапшоты `base-clean` есть.

**Типичные затыки:** Wazuh падает на 4 ГБ RAM (нужно 8); забытый `vm.max_map_count`; Windows не видит сеть, потому что бридж без порта — это нормально, но DHCP должен быть (поставь dnsmasq на SIEM или статические IP).

### Фаза 2. Телеметрия — 3–4 ч

Это фаза, которую джуны пропускают, а она даёт больше всего баллов на собесе. Без неё ты детектишь только то, что случайно попало в лог.

**Windows:**
```powershell
# 1. Аудит
auditpol /set /subcategory:"Process Creation" /success:enable
auditpol /set /subcategory:"Logon" /success:enable /failure:enable
auditpol /set /subcategory:"Account Logon" /success:enable /failure:enable
auditpol /set /subcategory:"Other Object Access Events" /success:enable /failure:enable
auditpol /set /subcategory:"Audit Policy Change" /success:enable
auditpol /set /subcategory:"Security Group Management" /success:enable /failure:enable

# 2. Командная строка в 4688 (GPO "Include command line in process creation events")
reg add "HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Policies\System\Audit" /v ProcessCreationIncludeCmdLine_Enabled /t REG_DWORD /d 1 /f

# 3. Script Block Logging (EventID 4104)
reg add "HKLM\SOFTWARE\Policies\Microsoft\Windows\PowerShell\ScriptBlockLogging" /v EnableScriptBlockLogging /t REG_DWORD /d 1 /f

# 4. Sysmon (конфиг sysmon-modular или SwiftOnSecurity)
sysmon64.exe -accepteula -i sysmonconfig.xml
```

**Wazuh-агент** (`C:\Program Files (x86)\ossec-agent\ossec.conf`) — добавить каналы:
```xml
<localfile>
  <location>Microsoft-Windows-Sysmon/Operational</location>
  <log_format>eventchannel</log_format>
</localfile>
<localfile>
  <location>Microsoft-Windows-PowerShell/Operational</location>
  <log_format>eventchannel</log_format>
</localfile>
```
`Security`, `System`, `Application` Wazuh берёт по умолчанию — проверь, что они реально идут.

**Проверка каждого источника руками** (это и есть суть фазы):
- `whoami /priv` и `cmd /c echo test` → Sysmon EventID 1 и Security 4688 с командной строкой;
- `schtasks /create /tn test /tr calc.exe /sc once /st 23:59` → 4698;
- `powershell -enc <base64>` → 4104;
- 5 неудачных логинов → 4625.

**DoD:** заполнен `docs/telemetry-matrix.md`: для каждой строки — «проверено, событие нашёл в Wazuh, `rule.id = ...`, поля такие-то». Незаполненные строки — это твои будущие «gaps», их тоже фиксируй.

### Фаза 3. Три атаки — 4–5 ч

Правила: снапшот перед каждым тестом, время **в UTC**, фиксируй `start/end`, не перезагружай VM между атакой и разбором.

1. **T1059.001** — Atomic Red Team:
```powershell
IEX (IWR https://raw.githubusercontent.com/redcanaryco/invoke-atomicredteam/master/install-atomicredteam.ps1 -UseBasicParsing)
Install-AtomicRedTeam -getAtomics
Invoke-AtomicTest T1059.001 -TestNumbers 1
```
Если на жертве нет интернета — скачай атомики на хосте и скопируй папку.

2. **T1053.005** — создание задачи через `schtasks` и через PowerShell `Register-ScheduledTask` (две разные телеметрии — сравни).

3. **T1110.003** — password spray с Kali по SMB:
```bash
nxc smb 10.10.10.20 -u users.txt -p passwords.txt
```
(если SMB не отвечает — fallback: SSH-брутфорс по Linux-жертве через `hydra`, тогда лог-сорс `auth.log`, а детект — по частоте 5712/5760).

На каждую атаку сохрани: скриншот алерта, JSON события, точные UTC-таймстемпы, `rule.id`, и отдельно — **чего в логах не было**.

**DoD:** три папки в `evidence/`, по каждой — скриншот + таймстемпы + заметка о пробелах. Хотя бы для одной атаки зафиксировано «детекта не было / был FP».

### Фаза 4. Три отчёта — 4–5 ч

Пиши по шаблону из §6. Объём — 1–2 страницы, не больше: на собеседовании их читают 40 секунд.

Обязательные элементы: Summary → Timeline (UTC) → IOCs → ATT&CK → Detection (какой лог/правило) → False positives → Gaps → Recommendation.

Один из трёх отчётов сделай про **неудачу**: «правило не сработало, вот почему, вот что я поменял». Это самый ценный документ в репозитории.

**DoD:** три отчёта в `reports/`, у каждого заполнены все секции, включая Gaps и Recommendation.

### Фаза 5. Пять детектов — 3–4 ч

1. Напиши 5 Sigma-правил (можно простых) — по одному на технику + 2 вариации (например, encoded PowerShell и его обход через `-EncodedCommand` в нижнем регистре).
2. Для каждого проверь **FP**: запусти легитимную активность (штатный `schtasks`, админский PowerShell) и убедись, что правило не спамит. Если спамит — сузь и запиши, что изменил.
3. Конвертируй 1–2 правила в формат Wazuh и добейся реального алерта на стенде.
4. Заполни detection card по шаблону из §7.

**DoD:** 5 карточек, у каждой есть секция «FP-анализ» с конкретикой, а не «FP возможны».

### Фаза 6. Упаковка — 3–4 ч

1. `README.md`: схема (draw.io/Excalidraw), таблица VM, 2 абзаца «зачем», раздел «Ограничения» и «Что дальше».
2. Видео 5 минут (OBS): 30 сек — кто ты и что за стенд; 2 мин — запуск атаки; 2 мин — разбор в SIEM (искать по полям, а не просто «вот алерт»); 30 сек — gaps и что дальше. Голос обязателен, без голоса ценность падает вдвое.
3. One-pager PDF: схема + 3 техники + 5 детектов + 1 инсайт + ссылка на репозиторий.
4. Обнови резюме (формулировки в §11) и LinkedIn.

**DoD:** ссылка на репозиторий открывается в инкогнито, видео играет, в one-pager нет опечаток.

### Фаза 7. Подготовка к собесу — 2–3 ч

1. Прогони вопросы из §10 вслух, не про себя.
2. Собери 3 истории по STAR: «нашёл слепую зону», «разобрал FP», «не хватило данных — что сделал».
3. Отрепетируй 5-минутную демонстрацию (§9) дважды с таймером.
4. Заранее ответь себе: «почему ты выбрал Wazuh, а не Security Onion?» — ответ должен быть про цель, а не про «так в туториале».

**DoD:** демо укладывается в 5 минут, на каждый вопрос есть ответ на 60–90 секунд.

## 6. Шаблон incident report

```markdown
# INC-001 — PowerShell execution (T1059.001)

**Дата:** 2026-11-01 | **Автор:** ... | **Severity:** Medium | **Статус:** Closed

## Summary
Одна-две фразы: что произошло, на каком хосте, чем закончилось.

## Environment
Хост, ОС, IP, роль, агент/версия SIEM, источник логов.

## Timeline (UTC)
| Время | Событие | Источник | Event ID |
|---|---|---|---|
| 12:00:01 | запуск powershell.exe -enc ... | Sysmon | 1 |
| 12:00:01 | script block | PowerShell | 4104 |
| 12:00:03 | алерт | Wazuh | rule.id=... |

## Detection
Какое правило сработало, по какому полю, через сколько секунд после действия.
Если не сработало — почему (нет лога / нет правила / правило есть, но поле другое).

## IOCs
Хеши, IP, домены, командные строки, ключи реестра. Если нет — «отсутствуют, техника локальная».

## MITRE ATT&CK
T1059.001 — Command and Scripting Interpreter: PowerShell.

## False positives
Что ещё может вызвать такое же событие. Как отличить.

## Gaps
Чего не хватило: выключенный аудит, отсутствующий канал, поля нет в декодере.

## Recommendation
1–3 конкретных действия: включить X, добавить правило Y, сузить Z.

## Lessons learned
Одна фраза «что бы я сделал иначе».
```

## 7. Шаблон detection card

```markdown
# DET-001 — Encoded PowerShell

**Техника:** T1059.001 | **Источник:** Sysmon 1, PowerShell 4104 | **Severity:** Medium

## Гипотеза
Если злоумышленник запускает PowerShell с `-enc`, я увижу base64 в командной строке
и/или в 4104.

## Логика
- field: `win.eventdata.commandLine`
- match: `-enc` / `-EncodedCommand` (case-insensitive)
- НЕ считать: parent = устаревший установщик (уточнить по инвентарю)

## Sigma
```yaml
title: Encoded PowerShell Execution
id: 00000000-0000-0000-0000-000000000001
status: experimental
logsource:
  product: windows
  category: process_creation
detection:
  selection:
    Image|endswith: '\powershell.exe'
    CommandLine|contains:
      - ' -enc '
      - ' -EncodedCommand '
  condition: selection
level: medium
```

## Проверка
| Тест | Результат | Скриншот |
|---|---|---|
| Atomic T1059.001 #1 | алерт есть, задержка 2 с | evidence/t1059/01.png |
| Штатный PowerShell ISE | FP нет | — |

## FP-анализ
Что запускал специально, чтобы поймать ложное срабатывание. Итог: ...

## Ограничения
Не ловит обфускацию без `-enc`; не ловит PowerShell 7 с другим именем бинаря.
```

## 8. Шаблон telemetry matrix

| Источник | Event ID | Что вижу | Включено | Проверено | Примечание |
|---|---|---|---|---|---|
| Security | 4624 | успешный вход, тип логона | да | да | тип 3 = сетевой |
| Security | 4625 | неуспешный вход | да | да | нужен для T1110 |
| Security | 4688 | создание процесса + cmdline | да | да | только после включения GPO |

| Sysmon | 1 | процесс + командная строка + parent | да | да | |
| Sysmon | 3 | сетевые соединения | да | нет | выключено в конфиге → gap |
| Sysmon | 11 | создание файла | да | нет | |
| Sysmon | 13 | запись в реестр | да | нет | |

Пустые «Проверено» — это честные gaps, а не стыд. Именно они делают отчёт живым.

## 9. Сценарий демо на 5 минут

1. **0:00–0:30** — «Я собрал изолированный стенд: SIEM, Windows-жертва с Sysmon, Kali. Цель — пройти путь от атаки до отчёта.»
2. **0:30–2:30** — запуск атаки (T1053.005), на экране — команда и её вывод.
3. **2:30–4:30** — в Wazuh: Threat Hunting → фильтр по хосту и времени → нашли событие → открыли JSON → назвал поля → показал, что алерт указывает на конкретное правило. **Проговори вслух, почему это подозрительно.**
4. **4:30–5:00** — «Чего не хватило: [конкретный лог]. Что бы добавил: [конкретно]. Отчёт лежит в репозитории, ссылка в резюме.»

Не показывай дефолтный дашборд. Показывай **свой путь поиска**.

## 12. Урезанная версия на 8 часов

Если времени совсем нет — делай только это:

1. **2 ч** — VMware/Hyper-V: Windows 11 + Sysmon + Wazuh в Docker на той же машине (или Wazuh-агент на облачный триал — не критично).
2. **1 ч** — включить аудит и script block logging, проверить 4104 и 4688.
